## 2026-05-19 — Update: 기술 스택 전면 전환 (모바일 하이브리드 → 웹 풀스택)
- **트리거:** 사용자가 BMad 워크플로우 실습 목적으로 학습 대상 스택을 변경. "백엔드는 FastAPI", "DB 슈퍼베이스, 백엔드 FASTAPI, 프론트 NEXT JS".
- **결정 1 — 스택:** Frontend **Next.js**, Backend **FastAPI**, DB **Supabase (Postgres)**. n=1 / 인증 없음 유지.
- **결정 2 — 플랫폼 (NFR5 대체):** 데스크톱 + 모바일 브라우저 반응형 웹. PWA 미사용, 별도 모바일 앱 빌드 없음.
- **결정 3 — 오프라인 (NFR1 폐기):** 온라인 전제. 네트워크가 없으면 동작하지 않음. 낙관적 UI 미적용 (단순함 우선).
- **결정 4 — 클라우드 동기화 (4.2 항목 폐기):** Supabase로 클라우드 저장. 기존 Out of Scope에서 제거.
- **결정 5 — 리셋 기준 시계 (F3 유지):** 클라이언트 로컬 시간 기준. 기존 PRD 결정과 동일.
- **결정 6 — 브리프 처리:** brief.md(final)의 '결정 사항' 표 중 플랫폼/개발 방식/데이터 저장 행을 새 스택으로 동기화. 일반적으로 final 브리프는 동결하지만 사용자 명시 요청으로 갱신.
- **자동 폐기 항목:** NFR1(오프라인), 섹션 4.2의 "클라우드 동기화 제외" 줄, NFR5(Android 하이브리드).
- **Supabase + FastAPI 중복 인지:** Supabase 자체가 REST/Auth를 제공하지만 학습 목적으로 FastAPI를 의도적으로 중간 계층에 둠. 아키텍처 문서에서 "왜 굳이"를 명시할 예정 (다음 단계 `bmad-create-architecture`).
- **트레이드오프 기록:** "즉시 영속화"(FR1.3, FR2.3)는 온라인 전환으로 네트워크 RTT 만큼의 지연이 끼게 됨. 낙관적 UI를 의도적으로 도입하지 않으므로 NFR3(1초 가드)와의 정합성은 아키텍처 단계에서 다시 검토 필요. (Open Item으로 PRD에 남김.)
- **How to apply:** PRD 본문에서 모바일/하이브리드/오프라인/로컬 저장 관련 표현을 모두 웹/온라인/Supabase 기준으로 재작성. NFR 번호는 가능한 유지(NFR2=영속성, NFR3=속도, NFR4=단순성). NFR1과 NFR5는 의미를 바꾸지 말고 새 NFR로 교체(접근성·반응형 등).
